# Codex Maestro 기능 기획 — 관계에서 검토 가능한 작업 전달로

작성일: 2026-10-03 · 범위: 이 Mac의 로컬 Codex 프로젝트와 세션 · 상태: 제품 제안

## 1. 권고

다음 MVP는 **네 종류의 방향 관계를 통해 근거를 모으고, 지정한 세션 하나에 검토 가능한 작업 초안을 전달하는 흐름**으로 정한다. 관계 수를 늘리는 것보다 사용자가 “어떤 근거를 누구에게 전달하며, 무엇이 아직 끝나지 않았는가”를 판단할 수 있게 하는 것이 중요하다.

핵심 흐름은 `관계 선택 → 근거 선택 → 수신 세션 확정 → 초안 검토 → 명시적 전송 → 전송 상태 확인`이다. 프로젝트 목적지는 수신 세션을 고르기 전까지 전달 대기 항목으로 유지한다. 관계 저장, 프로젝트 소속, 프롬프트 전송, 작업 완료는 별개 상태다.

MVP에 포함할 기능은 관계 의미 정리, 출처를 보존하는 전달 묶음, 프로젝트 수신함과 세션 선택, 수동 프로젝트 참고자료, 결과 포인터, 전달 상태 기록이다. 선행 작업과 검토 요청에는 목적과 완료 조건을 기록하되, 자동 스케줄링은 넣지 않는다. 범위 검색, 수동 작업 추적, 검토 결과 회수는 다음 단계다. 무인 오케스트레이션은 실제 전송 E2E와 복구 계약을 검증한 뒤 별도로 판단한다.

이 문서는 구현 승인이 아니다. 이 기획 작업은 이 파일만 추가하며 Swift, 테스트, 기존 문서, 사용자 작업공간을 변경하지 않는다.

## 2. 현재 기능과 근거 경계

아래 내용은 작성 시 읽은 소스의 관찰이다. 동시 구현 세션이 혼합 연결을 추가 중이므로, 구현 이후의 최종 기능 목록으로 사용하지 않는다. 여기서 새 빌드, UI 실행, 실제 프롬프트 전송을 수행하지 않았다.

| 확인 대상 | 소스에서 확인한 동작 | 기획에 미치는 영향 |
|---|---|---|
| 프로젝트·세션 모델 | `Session.projectID`, `parentID`, 상태와 실시간 연결 여부가 별도로 존재한다. `SessionLink`와 `ProjectLink`에는 방향, 목적, 메모가 있다. | 소속·계보·사용자 관계를 합치지 않는다. |
| 관계 관리 | 작성 시작 시 `ConnectionScope`는 프로젝트와 세션 두 범위다. 생성·편집·삭제, 현재 카탈로그의 대상 검사, 저장 실패 시 복원이 있다. | 혼합 연결은 진행 중인 기반 작업으로 취급한다. 이 문서는 해당 구현의 완료를 선언하지 않는다. |
| 전달 초안 | `prepareHandoff`는 출발 세션의 최근 저장 메시지 최대 10개 중 마지막 assistant 텍스트를 사용한다. 없으면 미리보기를 사용하며, 목적지의 기존 초안에 추가한다. | 전체 대화 복원이나 작업 요약이 아니다. 반복 추가, 오래된 내용, 미리보기 대체 여부를 드러낼 필요가 있다. |
| 프롬프트 전송 | `send`는 기존 세션 ID에 전송하고 성공 반환 뒤 동일한 초안을 지운다. 실패하면 오류를 기록한다. | 전송 반환과 모델 작업 완료를 구분하는 기록이 필요하다. |
| 탐색 | 최근 40개와 실시간 세션을 중심으로 표시한다. 검색은 제목·경로·ID·모델 문자열을 검사한다. | 현재 검색을 대화 본문 검색으로 표시하면 안 된다. |
| 상세·토폴로지 | 프로젝트/세션 상세, 관계 목적과 방향, 소속선, 부모 세션 탐색, 접기와 펼치기가 있다. | 새 기능은 기존 네이티브 상세 패널과 목록에 배치한다. 전체 그래프를 더 복잡하게 만들지 않는다. |
| 저장·활동 | 관계·위치·초안은 로컬 작업공간에 저장한다. 활동 이벤트는 메모리에서 최대 80개를 유지한다. 내보내기는 초안을 제외한다. | 지속적인 전달 이력과 결과 포인터는 새 저장 계약이 필요하다. |

근거 파일과 확인한 심볼:

- [README](../README.md): 제품 범위, 저장 위치, 로컬 어댑터 설명.
- [Models.swift](../Sources/MaestroCore/Models.swift): `Project`, `Session`, `LinkKind`, `WorkspaceState`.
- [MaestroStore.swift](../Sources/CodexMaestro/MaestroStore.swift): `filteredSessions`, `prepareHandoff`, `send`, `record`, `exportGraph`.
- [ProjectConnections.swift](../Sources/CodexMaestro/ProjectConnections.swift): `ConnectionScope`, 관계 CRUD, 편집 화면.
- [SessionInspector.swift](../Sources/CodexMaestro/SessionInspector.swift): 프로젝트 상세, 연결 목록, 초안 편집·전송.
- [TopologyCanvas.swift](../Sources/CodexMaestro/TopologyCanvas.swift): 그룹 배치, 접힌 세션, 정적·이동 연결선 분리.

[연동 계약](INTEGRATION.md)과 [검증 기록](VALIDATION.md)은 내부 IPC의 로컬 버전 의존성과 실제 프롬프트→모델 응답 완료 E2E 미검증을 명시한다. 이는 기존 기록이며 이번 기획에서 재검증하지 않았다. 소켓 fixture의 수락 응답은 실제 모델 완료 근거가 아니다. 공개 Codex 기능에 기대는 제안은 하지 않으므로, 새로운 공개 API 지원 주장을 추가하지 않는다.

[성능 기록](PERFORMANCE.md)은 601개 합성 세션 및 당시 606개 로컬 카탈로그 관찰을 구분한다. 숫자는 현재 카탈로그 크기가 아니다. 현재 캔버스는 펼친 카드를 모두 유지하며, 데이터 배치 계산 측정은 화면 프레임 성능을 보장하지 않는다.

## 3. 네 종류의 관계가 의미하는 것

관계의 두 끝점은 `(유형, ID)`로 식별한다. 같은 이름이나 같은 문자열 ID를 이유로 프로젝트와 세션을 동일시하지 않는다. UI에서 출발과 도착의 유형을 각각 표시한다. 역방향 관계는 별도 관계이며, 방향 변경은 이전 전송 기록을 바꾸지 않는다.

| 방향 | 구체적 사용 사례 | 출발 측이 제공하는 것 | 도착 측이 의미하는 것 |
|---|---|---|---|
| 프로젝트 → 프로젝트 | 공용 SDK의 변경 계약을 앱 프로젝트가 참고한다. | 사용자가 고른 API 계약, 결정, 결과 포인터. 프로젝트의 모든 대화를 뜻하지 않는다. | 해당 프로젝트의 참고 관계 또는 전달 수신함. 모든 소속 세션이 수신자가 되는 것은 아니다. |
| 세션 → 프로젝트 | 성능 조사 세션의 결과를 제품 프로젝트에 남긴다. | 선택한 메시지, 측정 결과, 미해결 항목. | 프로젝트 수준의 자료 등록 또는 담당 세션 미정의 작업 요청. 조사 세션의 소속은 바뀌지 않는다. |
| 프로젝트 → 세션 | 앱 프로젝트의 현재 제약을 새 구현 세션에 전달한다. | 선택·고정한 프로젝트 참고자료의 특정 버전. | 명시한 세션의 초안. 프로젝트 전체를 읽었다고 간주하지 않는다. |
| 세션 → 세션 | 구현 세션이 검토 세션에 변경 사항과 검증 근거를 넘긴다. | 선택한 작업 결과와 요청 범위. | 정확히 지정한 세션의 초안. 원래 세션의 권한이나 완료 상태가 전파되지 않는다. |

관계 목적은 모든 조합에서 같은 방향 규칙을 사용한다.

| 목적 | `A → B`의 의미 | 실행상 의미 |
|---|---|---|
| 컨텍스트 전달 | A의 선택한 근거를 B가 참고한다. | 명시적으로 초안을 준비할 때만 내용을 복사한다. 계속 동기화하지 않는다. |
| 선행 작업 | A의 명시한 산출물 또는 조건을 B의 작업이 필요로 한다. | 선행 조건을 기록한다. A가 idle이 됐다는 이유로 조건을 충족시키거나 B를 실행하지 않는다. |
| 검토 요청 | A의 선택한 결과를 B가 검토하도록 요청한다. | 검토 요청과 결과를 연결한다. 관계 생성 자체는 요청 전송이 아니다. |

프로젝트가 선행 작업의 출발이면 “프로젝트 전체 완료” 대신 API 버전, 문서, 테스트 결과 등 구체적 조건을 지정한다. 프로젝트가 도착이면 영향받는 작업 또는 세션을 별도로 지정할 수 있다. 같은 프로젝트 내부의 프로젝트→세션 관계도 소속선과 목적이 다르므로 허용할 가치가 있다. 소속 없는 세션 묶음은 합성 UI 그룹이므로 실제 프로젝트 수신함으로 취급하지 않는다.

참고·검토 관계의 순환은 허용한다. 선행 작업의 순환은 표시하고, 이후 실행 계획으로 변환할 때에는 해소 전 실행을 막는다. 관계 삭제는 과거 전달 기록이나 Codex 세션을 삭제하지 않는다.

## 4. 프로젝트 목적지의 수신 세션 선택

프로젝트는 프롬프트를 실행하는 주체가 아니다. 프로젝트 목적지에는 `참고자료 등록`과 `작업 전달`을 별도 동작으로 제공한다. 등록은 Maestro의 로컬 자료만 갱신한다. 작업 전달은 아래 절차로 정확히 하나의 기존 세션을 선택한다.

1. 해당 프로젝트에 현재 속한 세션을 검색 가능한 목록으로 제시한다. 제목, 짧은 ID, 작업 경로, 브랜치, 모델·추론 수준, 실행 상태, 상태 확인 시각을 표시한다.
2. 사용자가 저장한 역할별 담당 세션을 우선 추천할 수 있다. 예: 구현 담당, 검토 담당. 추천 이유를 표시하며, 최근 업데이트 순서만으로 수신자를 확정하지 않는다.
3. 사용자가 수신 세션을 선택하면 전달 묶음에 프로젝트 ID와 실제 수신 세션 ID를 모두 고정한다. 프로젝트 기본 담당이 바뀌어도 이미 검토한 초안의 수신자는 바뀌지 않는다.
4. 최종 전송 직전에 대상 존재, 프로젝트 소속, 연결 상태, 초안 버전을 다시 확인한다. 변경이 있으면 전송을 멈추고 차이를 표시한다. 기존 검토를 새 대상에 적용하지 않는다.
5. 적합한 세션이 없으면 수신함에 `수신 세션 미지정` 상태로 남긴다. 사용자가 Codex에서 세션을 만들거나 연 뒤 카탈로그를 갱신하고 다시 선택한다.

실행 중이거나 사용자 입력을 기다리는 세션에는 MVP에서 전송을 막고 초안을 보존한다. 상태가 미확인이면 명시적인 갱신 또는 원래 Codex 확인을 안내한다. 이는 현재 전송 코드에 이미 있는 보장이라는 뜻이 아니라 제안하는 정책이다. 로컬 사전 검사 직후 상태가 바뀔 수 있으므로, 이 정책을 원자적인 실행 잠금으로 주장하지 않는다. 소유자 변경과 최종 수락은 어댑터의 별도 검증 대상이다.

담당 세션 삭제·보관·소속 변경 시 같은 이름의 다른 세션으로 대체하지 않는다. 다른 프로젝트 세션이 수신해야 한다면 사용자가 세션 목적지 관계를 명시적으로 선택한다. 프로젝트 관계를 숨은 교차 프로젝트 전송 경로로 사용하지 않는다. 한 프로젝트로 연결했다는 이유로 전체 세션에 브로드캐스트하지 않는다.

## 5. 기능 계약과 우선순위

우선순위는 P0=다음 MVP, P1=MVP 이후 실무 흐름, P2=연동 검증 이후 선택 확장이다. 아래 기능은 모두 제안이다. 각 기능의 수용 기준은 향후 구현에서 확보해야 할 근거이며 현재 통과했다는 뜻이 아니다.

### F1. 네 종류의 관계와 프로젝트 수신함 — P0

- **상황·의미:** 조사 세션에서 앱 프로젝트로 결과를 남기고, 실제 후속 작업 담당은 나중에 선택한다. 네 조합 모두 지원하되 도착이 프로젝트이면 자료 등록과 작업 전달을 구분한다.
- **입력 → 출력:** 끝점 유형·ID, 목적, 메모, 선택한 요청 → 관계와 전달 대기 항목. 관계 자체와 각 전달 시도는 별도 ID를 갖는다.
- **실행 경계:** 관계 생성·편집·수신함 등록은 로컬 저장만 수행한다. 세션 소속, 프로젝트 루트, 모델 설정은 바꾸지 않는다. 전송은 선택된 세션 하나에만 수행한다.
- **실패 처리:** 누락 대상은 ID와 마지막 표시 이름을 남긴다. 저장 실패 시 이전 관계와 편집 내용을 보존한다. 담당 세션 변경 시 기존 초안은 재지정하지 않는다.
- **의존성:** 현재 진행 중인 혼합 연결 구현과 저장 호환성. 수신함은 그 위에 추가한다.
- **수용 근거:** 네 조합의 생성·수정·재시작 후 복원, 구버전 파일 보존, 실패 저장 복원. UI에서 방향·유형·누락 대상을 식별한다. 관계 저장 시 전송 0회, 소속 변경 0회, 수신자 선택 후 다른 세션 전송 0회를 격리 테스트로 확인한다.

### F2. 출처를 보존하는 전달 묶음 — P0

- **상황·의미:** SDK 조사 결과를 앱 구현에 전달하되, 마지막 답변에서 빠진 제약과 미완료 검증을 함께 전달한다. 출발이 프로젝트이면 선택한 자료만, 세션이면 선택한 메시지·결과만 사용한다.
- **입력 → 출력:** 사용자 선택 근거, 목적, 요청 범위, 완료 조건 → 편집 가능한 초안과 출처 목록. 출처에는 세션 ID/메시지 ID 또는 파일 경로, 수집 시각, 내용 범위, 가능한 버전·해시를 기록한다. 메시지별 작성 시각을 얻지 못하면 수집 시각과 구분해 미확인으로 둔다.
- **실행 경계:** 최초 구현은 규칙 기반 템플릿과 사용자 편집으로 만든다. 내용을 요약하기 위해 숨은 모델 호출을 하지 않는다. 다른 세션의 텍스트는 참고자료로 구분하며 실행 지시로 자동 승격하지 않는다.
- **실패 처리:** 저장 대화 없음, 미리보기 대체, 내용 잘림, 오래된 자료를 명시한다. 큰 자료는 포함 범위를 선택하게 하며 조용히 자르지 않는다. 같은 묶음을 다시 준비하면 기존 초안을 덮어쓰거나 중복 추가하지 않고 사용자에게 병합 또는 새 버전 선택을 제공한다. 비동기 수집 중 목적지 초안이 바뀌면 변경을 보존한다.
- **의존성:** F1의 끝점 의미, F3의 프로젝트 자료. 세션→세션은 먼저 적용할 수 있다.
- **수용 근거:** 기존 초안 보존, 중복 준비, 출처 변경, 수집 중 선택 변경, 자료 누락, 저장 실패를 검증한다. 준비만으로 전송되지 않아야 한다. 실제 UI에서 사용자가 포함·제외한 근거와 최종 프롬프트가 일치하는지 확인한다.

권장 초안 필드는 `요청`, `적용 범위`, `확정한 결정·제약`, `근거`, `미해결 사항`, `완료 조건`이다. 모든 필드를 의무 입력으로 만들지 않는다. 최근 저장 응답만 사용했다면 그 범위를 제목 가까이에 표시한다.

### F3. 프로젝트 참고자료 — P0는 수동 등록, P1은 갱신 비교

- **상황·의미:** 공용 라이브러리의 API 계약과 프로젝트별 검증 명령을 구현·검토 세션에서 재사용한다. 프로젝트→프로젝트는 참고 관계, 프로젝트→세션은 선택한 자료의 전달이다.
- **입력 → 출력:** 사용자가 선택한 짧은 결정 메모, 로컬 파일, 세션 결과 포인터 → 프로젝트별 참고자료 목록과 선택 시점의 전달 스냅샷.
- **실행 경계:** Maestro 메타데이터에만 등록한다. 저장소 전체 탐색, `AGENTS.md` 수정, 다른 세션 컨텍스트 주입을 자동 수행하지 않는다. 원본 파일을 열거나 내용을 포함하는 동작은 별도로 표시한다.
- **실패 처리:** 이동·삭제·수정된 파일은 경고한다. 저장한 스냅샷과 현재 원본을 구분한다. 이전 자료를 자동 최신본으로 치환하지 않는다. 링크 삭제는 원본 파일을 삭제하지 않는다.
- **의존성:** F2의 출처 구조. P1에서 버전 비교와 갱신 요청을 추가한다.
- **수용 근거:** 원본 변경 전후 표시, 재시작 후 참조 복원, 자료만 등록했을 때 원본·Codex 데이터 쓰기 0회. 권한 없는 파일과 누락 파일을 UI에서 구분한다.

### F4. 결과·산출물 포인터 — P0는 첨부, P1은 관계별 이력

- **상황·의미:** 빌드 성공 로그, PR, 변경 파일, 스크린샷을 작업 결과에 연결한다. 세션→프로젝트는 결과 등록, 세션→세션은 검토 근거 전달에 사용한다.
- **입력 → 출력:** 로컬 경로 또는 사용자가 제공한 URL, 설명, 생성 출처, 검증 종류 → 클릭 가능한 포인터와 근거 상태. 소스 확인·빌드·테스트·런타임·실기기·배포를 각각 기록한다.
- **실행 경계:** 포인터 추가는 파일 업로드, PR 작성, 공개 공유, 테스트 실행을 하지 않는다. URL이 있다는 이유로 외부 내용을 자동 조회하지 않는다. 내보내기는 초안뿐 아니라 새로 추가된 자료 본문도 기본 제외하고 범위를 명시한다.
- **실패 처리:** 파일 누락, URL 접근 미확인, 브랜치·커밋 불일치를 표시한다. 연결 존재를 검증 통과로 간주하지 않는다. 상대 경로는 기준 프로젝트 루트와 함께 보존한다.
- **의존성:** F2 출처, F3 자료 목록. 검토 라우팅에서 재사용한다.
- **수용 근거:** 잘못된 경로·접근 불가 URL·기준 커밋 변경을 재현한다. 사용자 표시와 내보낸 데이터에서 검증 수준이 변하지 않아야 한다. 파일은 등록 전후 동일해야 한다.

### F5. 전달 기록과 연동 관측 — P0

- **상황·의미:** 타임아웃 후 같은 요청을 다시 보내도 되는지 판단한다. 네 조합 모두 원래 관계와 실제 수신 세션을 추적한다.
- **입력 → 출력:** 전달 묶음 버전, 수신자, 요청 식별자, 어댑터 관측 → 지속되는 상태 기록. 초안, 전송 시도, 어댑터 수락 확인, 전달 결과 미확인, 실패를 구분한다. 세션 실행 상태와 작업 완료 판정은 다른 필드다.
- **실행 경계:** IPC 수락을 모델 완료로 표시하지 않는다. 자동 재전송을 하지 않는다. 중단·오프라인 상태에서도 로컬 자료 열람을 유지한다. 기록에는 진단용 메타데이터를 우선 저장하고 본문 복제·보존 기간은 별도 정책으로 정한다.
- **실패 처리:** 전송 중 연결 종료와 앱 재시작은 수락 증거가 없으면 `결과 미확인`으로 남긴다. 사용자가 원래 Codex에서 확인한 뒤 새 시도로 재전송할 수 있다. 관측 이벤트가 늦거나 다른 작업에서 왔으면 해당 요청 완료와 연결하지 않는다. 로컬 기록 저장 실패 시 새 전송을 시작하지 않는다.
- **의존성:** F2 전달 ID, 기존 내부 IPC 어댑터. 수락·턴·결과 상관관계를 얻을 수 있는지는 별도 검증한다.
- **수용 근거:** 격리 소켓에서 수락, 거절, 타임아웃, 소유자 변경, 단절, 재시작을 확인한다. 중복 전송이 없어야 한다. 사용자가 별도로 허용한 폐기 가능한 실제 세션에서 정확한 요청·수신자·응답 완료를 확인해야 실제 E2E로 기록할 수 있다. 이 기획은 해당 전송을 실행하지 않는다.

### F6. 작업·선행 조건 추적 — P1

- **상황·의미:** API 변경 결과가 나오기 전 앱 마이그레이션을 시작하지 않도록 작업을 관리한다. 프로젝트/세션 네 조합의 선행 관계에 구체적 작업 항목을 붙인다.
- **입력 → 출력:** 작업 설명, 담당 끝점, 충족 조건, 근거 포인터 → 준비·진행·차단·검토 필요·완료 상태와 미충족 조건 목록. 세션 하나에 여러 작업을 연결할 수 있다.
- **실행 경계:** 사용자 또는 검토된 결과 등록이 조건을 충족시킨다. 세션 idle, 마지막 답변의 완료 표현, 최근 업데이트 시각으로 작업을 완료시키지 않는다. 프로젝트 완료율은 정의한 작업 집합에만 적용한다.
- **실패 처리:** 순환 의존, 조건 없는 선행 관계, 삭제된 담당, 결과 버전 변경을 표시한다. 상위 결과 수정 시 이미 완료한 작업을 자동 재실행하지 않고 재검토 필요로 표시한다.
- **의존성:** F1·F4·F5. 독립적인 범용 이슈 트래커를 만들지 않고 관계에 필요한 작업 정보만 둔다.
- **수용 근거:** idle 전환으로 완료되지 않음, 조건 일부만 충족됨, 순환, 근거 갱신, 담당 변경을 검증한다. 전송 없이 수동 작업 상태를 관리할 수 있어야 한다.

### F7. 검토 라우팅과 결과 회수 — P1

- **상황·의미:** 구현 세션의 특정 변경을 해당 프로젝트의 검토 담당 세션에 보낸다. 세션→프로젝트 요청을 수신 세션으로 해석하며, 프로젝트→세션은 검토 기준을 제공한다.
- **입력 → 출력:** 대상 결과 버전, 검토 범위, 완료 기준, 선택한 검토 세션 → 검토 초안과 원요청에 연결한 결과 포인터. 반대 방향 연결을 자동 생성하거나 답변을 다른 세션에 자동 전달하지 않는다.
- **실행 경계:** 지정한 세션에 대한 명시적 전송만 허용한다. 검토 결과를 적용하거나 커밋·병합·배포하지 않는다. 기존 모델·추론 수준을 유지하고 검토 역할이라는 이유로 모델을 바꾸지 않는다.
- **실패 처리:** 구현 이후 결과가 바뀌면 검토 기준 버전과 차이를 표시한다. 작성자와 검토자가 같은 세션이면 표시한다. 담당 부재는 프로젝트 수신함에서 보존한다.
- **의존성:** F2·F4·F5, 완료 조건 연결에는 F6.
- **수용 근거:** 검토 대상 버전 고정, 수신자 변경 시 재검토, 결과의 원요청 연결, 원치 않는 역방향 전송 0회. 검토 답변 존재와 지적 반영 완료를 구분하는 UI를 확인한다.

### F8. 범위 검색과 근거 있는 요약 — P1, 모델 요약은 P2

- **상황·의미:** 600개 이상 세션 중 현재 앱의 API 결정을 찾는다. 선택한 프로젝트, 세션, 직접 연결 이웃으로 범위를 명시한다.
- **입력 → 출력:** 검색어, 범위, 메타데이터/저장 대화/등록 자료 구분 → 출처와 검색 범위가 표시된 결과. 초기 요약은 선택 자료의 발췌와 사용자가 확정한 결정 목록이다.
- **실행 경계:** 연결된 전체 그래프를 재귀 탐색하지 않는다. 저장 대화 검색은 지원되는 데이터 범위와 색인 시각을 표시한다. 향후 모델 요약은 대상·모델·전달 내용이 드러나는 별도 실행으로 제공한다.
- **실패 처리:** 색인 미완료, 읽기 실패, 투영 데이터 없음, 결과 잘림을 `검색 결과 없음`과 구분한다. 요약에서 출처가 없는 주장은 미확인으로 두고 새 사실로 저장하지 않는다.
- **의존성:** F3·F4, 증분 로컬 색인·취소 가능한 조회. 현재 제목 검색을 먼저 범위 선택과 연결한다.
- **수용 근거:** 601개 이상 고정 fixture에서 정답이 알려진 질의를 실행해 누락·오포함을 확인한다. 실제 Mac에서 입력 응답성과 취소를 측정한다. 불완전한 저장 이력을 전체 역사 검색으로 표시하지 않아야 한다.

### F9. 필요한 변화만 알리는 알림 — P1

- **상황·의미:** 사용자가 선택한 검토 세션의 입력 대기나 전달 실패를 놓치지 않는다. 프로젝트 구독도 실제 관심 작업·세션 목록으로 범위를 고정한다.
- **입력 → 출력:** 명시한 관찰 범위, 상태 전이, 전달 기록 → 앱 내 알림. 시스템 알림은 사용자가 활성화한 경우에만 제공한다.
- **실행 경계:** 알림은 새 턴을 시작하거나 승인 요청에 응답하지 않는다. running→idle은 `실행 상태 변경`으로 알리고, 요청과 결과가 확인되지 않으면 작업 완료라고 알리지 않는다.
- **실패 처리:** 최초 스냅샷·재연결 재생·중복 이벤트를 새 변화로 알리지 않는다. 연결 단절은 상태 미확인으로 구분한다. 앱 종료 중 감시는 별도 상주 실행이 없으면 제공하지 않는다고 표시한다.
- **의존성:** F5의 상태 구분, F6의 작업 판정. 백그라운드 서비스는 초기 범위 밖이다.
- **수용 근거:** 동일 이벤트 반복, 재연결, 소유자 변경, 알림 해제, 상태 누락 시나리오에서 중복·허위 완료 알림이 없어야 한다. 실제 macOS 알림 권한과 클릭 후 원래 세션 이동을 확인한다.

### F10. 검토 가능한 실행 계획 — P2

- **상황·의미:** API 조사→구현→검토를 순서대로 수행한다. 기존 관계 중 사용자가 선택한 작업만 실행 계획으로 변환한다. 관계 그래프 전체를 실행 그래프로 간주하지 않는다.
- **입력 → 출력:** 단계별 고정 수신자, 근거 버전, 선행 조건, 각 단계의 프롬프트, 종료 조건 → 실행 전 미리보기와 단계별 기록. 초기 버전은 `다음 초안 준비`를 안내하는 방식으로 제한한다.
- **실행 경계:** 매 단계 전송은 명시적 행동이다. 향후 무인 실행을 제공하려면 대상·횟수·실행 조건·중지 조건을 별도로 승인받는 제품 계약이 필요하다. 관계 저장이나 계획 생성은 실행 승인이 아니다. 파일 변경 충돌을 관계만으로 해결할 수 없다.
- **실패 처리:** 순환, 근거 변경, 수신자 변경, 승인 대기, 결과 미확인, 같은 checkout의 병행 쓰기 가능성이 있으면 후속 단계를 멈춘다. 재시작 후 자동 재개하지 않는다. 중지 버튼은 후속 전송을 차단하며 이미 실행 중인 Codex 턴 취소는 지원·검증된 경우에만 약속한다.
- **의존성:** F5 실제 E2E, F6 완료 조건, F7 결과 계약, 명시적 실행 취소·중복 방지·호환성 정책. 현재 내부 IPC가 이 계약을 제공한다는 보장은 없다.
- **수용 근거:** dry run의 전송 0회, 조건 미충족 시 후속 전송 0회, 단계별 대상 고정, 중단·재시작·타임아웃 복구를 확인한다. 실제 세션 E2E와 사용자 관찰 없이 무인 실행을 출시하지 않는다.

## 6. 네이티브 화면과 600개 이상 세션

주 작업 화면은 사이드바의 범위 선택, 중앙 목록/토폴로지, 오른쪽 상세 패널을 유지한다. 연결 관리에서는 출발·도착의 유형을 각각 선택하고 검색으로 대상을 좁힌다. 긴 세션 목록을 단일 메뉴에 모두 넣지 않는다. 제목이 같은 세션은 프로젝트·경로·짧은 ID로 구분한다.

프로젝트 상세에는 참고자료, 미지정 전달, 담당 세션을 둔다. 세션 상세에는 받은 요청, 전달 초안, 결과 포인터를 둔다. 관계 상세에는 목적, 방향, 근거와 전달 이력을 둔다. 전체 그래프에는 원문이나 장문 요청을 표시하지 않는다. 선택한 노드의 직접 관계를 우선 표시하고, 숨겨진 상대와 관계 수를 목록에서 확인할 수 있게 한다.

색상만으로 유형이나 상태를 구분하지 않는다. 방향 텍스트, 끝점 유형, 아이콘과 상태명을 함께 제공한다. 키보드로 검색→대상 선택→초안 검토→전송까지 이동할 수 있어야 한다. 프로젝트 필터 선택과 캔버스 노드 선택은 기존처럼 별개로 유지한다.

성능 수용 목표는 구현 전 측정 환경과 함께 고정한다. 제안 목표는 601개 이상 카탈로그에서 캐시된 범위 검색의 입력 후 결과 표시 p95 200ms 이하, 상세 선택 후 첫 메타데이터 표시 p95 100ms 이하이다. 측정은 release 앱에서 반복하며 콜드/웜 상태를 분리한다. 이는 현재 달성 수치가 아니다. 대화 읽기와 색인은 비동기로 수행하고 이전 조회를 취소할 수 있어야 한다.

UI 검증은 전체 목록, 접힌 프로젝트, 혼합 연결 밀집 그래프, 드래그 중 상태 갱신을 포함한다. 데이터 계산 시간, 프레임 측정, 실제 사용자 드래그 관찰을 각각 기록한다. 새 전달 이력과 원문 데이터가 카드 드래그 때 전체 캔버스를 다시 계산하게 만들지 않는다. 목록 가상화와 캔버스 가시 영역 제한은 측정에서 병목이 확인되면 적용한다.

## 7. 저장과 연동 원칙

저장 구조는 관계, 참고자료, 전달 묶음, 전달 시도, 작업 항목을 구분한다. 특정 Swift 타입이나 즉시 스키마 교체를 요구하지 않는다. 현재 혼합 연결 구현을 확인한 뒤 최소 변경으로 합의한다.

- 관계는 안정적인 끝점과 목적을 보존한다. 전달 묶음은 선택한 내용 버전을 고정한다. 전달 시도는 실제 수신 세션과 전송 결과를 기록한다.
- 기존 작업공간의 관계·배치·초안을 유지한다. 마이그레이션은 구버전 읽기, 저장 실패, 알 수 없는 버전, 손상 파일을 포함해 검증한다. 원본 손상 파일을 빈 상태로 덮어쓰지 않는다.
- 읽기 전용 Codex DB와 Maestro 소유 데이터의 경계를 유지한다. 인증·설정·기록을 직접 수정하지 않는다. 새 데이터도 현재 로컬 파일 접근 정책을 유지한다.
- 현재의 “초안 제외 내보내기”를 새 원문·자료 본문에도 확장한다. 관계 메모와 파일 경로도 내보내기에 포함될 수 있음을 보여준다. 로컬 전용이라도 내보내기는 별도 데이터 경계다.
- 내부 IPC 버전 불일치 시 실행 기능을 중단하되 로컬 관계·자료 열람은 유지한다. 버전 문자열만으로 호환을 확정하지 않고 필요한 메시지 구조와 동작을 검증한다.
- 별도 app-server를 시작해서 기존 데스크톱 세션의 소유권·승인·모델 설정을 우회하는 대체 경로를 만들지 않는다. 새로운 연동 방식은 별도 제품 범위와 검증이 필요하다.

## 8. 출시 순서와 판단 기준

| 단계 | 제공 가치 | 포함 범위 | 다음 단계 진입 근거 |
|---|---|---|---|
| 기반 통합 | 네 종류의 관계를 오해 없이 기록 | 진행 중인 혼합 연결, 방향·유형 표시, 저장 호환성 | 네 조합 CRUD·복원·실패 보존, 소속 변경·자동 전송 없음, 실제 UI 확인 |
| MVP | 정확한 근거를 한 세션에 전달 | F1–F5. 수동 자료와 포인터, 프로젝트 수신자 선택, 검토 초안, 전달 기록 | 기존 회귀 검사, 실제 macOS 핵심 흐름, 별도 허용된 실제 전송 E2E. E2E 전에는 로컬 계획·초안 기능과 실험적 전송을 구분 |
| 실무 확장 | 미완료 작업·검토·과거 결정을 회수 | F6–F9, F3·F4의 이력 확장 | 알려진 작업 시나리오의 누락·오라우팅·중복 알림 검사, 600개 이상 탐색 성능과 사용성 측정 |
| 선택적 자동화 | 반복 전달의 수동 단계를 줄임 | F10. 우선 단계별 초안 안내 | 실제 요청-결과 상관관계, 중단·재시작·불확실 전송 복구, 사용자 지정 실행 범위 계약 |

MVP의 대표 수용 시나리오는 “SDK 조사 세션의 근거를 앱 프로젝트 수신함에 등록하고, 담당 구현 세션을 선택해 초안을 검토한 뒤 전송 상태를 확인한다”이다. 이어 프로젝트 참고자료를 검토 세션에 전달하고 결과 포인터를 등록한다. 이 두 흐름으로 네 종류의 관계를 모두 다루되, 여러 세션을 동시에 자동 실행하지 않는다.

제품 효과는 사용자 통제 없이 전송을 늘린 횟수로 측정하지 않는다. 반복 작업에서 근거를 다시 찾는 시간, 정확한 수신자를 고르는 시간, 오래된 근거를 발견한 비율, 전달 결과 미확인 항목을 해소하는 시간을 로컬 관찰로 비교한다. 오대상 전송, 기존 초안 유실, 중복 전송, 프로젝트 소속의 암묵적 변경은 허용하지 않는 회귀 조건이다.

## 9. 구현 전에 확정할 소수의 결정

1. 혼합 연결 구현의 최종 끝점 식별·저장 방식과 이 문서의 의미가 일치하는지 확인한다. 이 계획 때문에 동시 구현을 다시 작성하지 않는다.
2. MVP 전달 묶음의 최소 필드를 합의한다. 권고는 요청·근거·미해결 사항·완료 조건과 고정 수신자다.
3. 프로젝트 목적지의 기본 행동은 로컬 수신함 등록으로 정한다. 역할별 담당은 추천만 하며 명시적 선택 후 전송한다.
4. 전달 이력 보존 범위와 새 내보내기 필드를 확정한다. 전체 대화를 중복 저장하는 설계는 MVP에서 제외한다.
5. 실제 전송 E2E를 수행할 폐기 가능한 세션과 허용 범위를 별도로 정한다. 검증 전에는 완료 추적·자동 재시도·무인 실행을 약속하지 않는다.

이 우선순위는 현재 앱의 강점인 로컬 탐색, 네이티브 상세 패널, 검토 후 전달을 확장한다. 다음 구현 단위는 더 많은 자동화보다 **근거를 고정한 전달 묶음과 프로젝트 수신자 선택**이 적절하다.
